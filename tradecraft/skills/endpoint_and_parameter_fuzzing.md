Parameter discovery (`arjun`) and endpoint fuzzing (`ffuf`) are most effective when sequenced after initial fingerprinting (`httpx_probe`, `whatweb`, `gau`):

- **Parameter Fuzzing Prerequisites & Wordlist Sizing (`arjun`):**
  Only run `arjun` against endpoints that return valid interactive responses (HTTP 200, 301/302 redirects, or API endpoints). Do not fuzz parameters against a root or path that returns HTTP 403 Forbidden or 404 Not Found — a denied path rejects parameter permutations uniformly. Discover a reachable path first with `ffuf` or `katana`, then probe that path with `arjun`. When probing direct origins, VPSs, or shared hosting (e.g. cPanel, Hostnet, Locaweb) lacking a CDN/WAF, use `wordlist="small"` (default top ~800 parameters); Arjun's differential batching sends only ~20–40 HTTP requests on `small`, avoiding host firewall connection tripwires. Reserve `wordlist="medium"` or `"large"` for targets behind elastic CDNs (like Cloudflare).
- **Passive Archive Harvesting as Wordlist Feedstock (`gau`):**
  `gau` queries third-party passive archives (Wayback, Common Crawl, OTX) without sending traffic to the target host or tripping WAFs. Always query `gau` ONLY against the primary apex/registrable domain (e.g. `examplepaint.com.br`), even if the apex is behind a CDN/WAF. Do NOT run `gau` against leaf third-party SaaS subdomains (such as `*.pages.rdstation.com.br` or specific leaf CNAME hosts); public archives do not catalog isolated tenant subdomains independently, causing timeouts without yielding records. Historical URLs and query parameters collected from the apex provide high-confidence endpoints and parameter names to test against direct origins and subdomains. If `gau` times out against a massive domain footprint, do NOT retry it in subsequent turns; upstream historical archives (Wayback/CommonCrawl) time out on domains with millions of URLs, so immediately pivot to active crawling (`katana`) rather than re-requesting.
- **Timeout vs. Sparse-Result Handling (any tool, not just `gau`):** A hard timeout error on a tool's first call against a target is a different signal from a sparse or empty *successful* result. A genuine timeout means whatever made the call slow (an oversized archive, an unresponsive endpoint, a rate limit) was still true at the moment it failed, so an unmodified identical retry is unlikely to succeed any better the second time. Don't retry identically; either narrow what's being asked (a smaller wordlist, a scoped query, one host instead of a batch) or pivot to a different tool/thread for that lead. A second identical attempt is reasonable only as a low-cost last-resort sweep once every other open lead has already been exhausted -- not as the default response to a timeout.
- **Immediate Parameter Attack Chaining (`sqlmap`, `commix`, `dalfox`):**
  When `katana`, `gau`, or `ffuf` surfaces interactive input parameters (e.g. `_action`, `id`, `q`, `cmd`, search parameters, form actions), do NOT defer parameter testing until after broad, noisy phases (like deep wordlist fuzzing or multi-tag nuclei runs). Fragile or shared backends (such as cPanel/shared hosting) can trip firewall rate-limits under prolonged traffic. Immediately test candidate parameters with `sqlmap`, `commix`, and `dalfox` while the target host and session are healthy and responsive. A newly-found, more interesting lead elsewhere does not deprioritize an already-discovered, already-untested parameter -- finish the cheap check (a `params_discovered`/`arjun_params_discovered` fact with no matching `sqli_tested`/`xss_tested`/`cmdi_tested` on that same host:port means it's still open) before following the more interesting thread; it will still be there afterward.
- **Exhaustive Parameter Exploitation Sequencing (`sqlmap`, `commix`, `dalfox`):**
  When an interactive parameter is identified, probe that parameter across the three core injection classes:
  1. Test with `sqlmap` (specifying `parameter` and `--batch`) to check for SQL injection / data extraction.
  2. Test with `commix` (specifying `parameter` and `--batch`) to check for OS command injection.
  3. Test with `dalfox` (specifying `parameter` or `data`) to check for Cross-Site Scripting (XSS).
  Do not stop after testing only one class — an input resistant to XSS may be vulnerable to SQL or command injection, and vice versa.
- **Targeted SQL Injection Testing (`sqlmap`):**
  Sequence `sqlmap` against parameters surfaced by `arjun`, `gau`, or `katana` that handle dynamic data (e.g. search queries, entity IDs, filters, user inputs). Specify `parameter` to test specific discovered inputs directly, rather than running unbounded crawl scans. Avoid running `sqlmap` against static assets or dead roots.
- **Targeted Command Injection Testing (`commix`):**
  Sequence `commix` against parameterized endpoints discovered by `katana` or `ffuf` that interact with backend system utilities, file processing, network diagnostics, or administrative tasks. Pass `parameter` to test specific inputs directly.
- **Targeted XSS Testing (`dalfox`):**
  Sequence `dalfox` against parameterized endpoints discovered by `arjun`, `gau`, or `katana` that reflect inputs or render dynamic content. Pass `parameter` to test specific inputs directly.
- **Local File Inclusion (LFI) Confirmation (`php_lfi`):**
  When PHP endpoints (`.php`) or file/template routing parameters (`page`, `file`, `include`, `template`, `view`, `layout`, `path`, `doc`, `action`) are surfaced by `arjun`, `gau`, or `katana`, sequence `php_lfi` with `target` and `parameter`. `php_lfi` executes bounded traversal sequences and PHP filter wrappers (`php://filter/convert.base64-encode/resource=...`) to confirm whether system files (such as `/etc/passwd` or `win.ini`) or base64-encoded PHP source code can be extracted without mutating server state.
- **Open Redirect Verification (`http_request`):**
  When `arjun`, `katana`, or `gau` discovers parameter names indicating navigation or redirect targets (e.g. `ReturnURL`, `returnUrl`, `redirect_to`, `redirect`, `next`, `url`, `dest`, `target`, `r`), do not only test for XSS. Verify open-redirect behavior by issuing an `http_request` with `follow_redirects=false` passing external target values (e.g. `https://example.com`, `//example.com`). Check the response status code (301, 302, 303, 307, 308) and verify whether the `Location` header reflects the untrusted external destination.
- **Shared Hosting Traffic Staggering:**
  When targeting shared hosting (e.g. Locaweb, cPanel) without a CDN/WAF: avoid blasting multi-tool concurrent fuzzing (e.g. running `arjun` + `ffuf` + `nuclei` in the same turn). Stagger content and parameter discovery across turns to prevent triggering host-level connection tracking limits (e.g. CSF `PORTFLOOD` or `CT_LIMIT`). For content discovery, prefer `ffuf(wordlist="small")` (top ~20 critical paths) and `arjun(wordlist="small")` to minimize request volume and keep the origin alive.
- **Single-Page Application (SPA) & Dynamic JS Crawling (`katana`):**
  When `whatweb` or `httpx_probe` detects modern JavaScript client frameworks (e.g. React, Angular, Vue, Next.js, Nuxt), standard static HTML scrapers only discover bundle script tags and empty root containers (`<div id="root">`). Run `katana` with `headless=true` to execute client-side JavaScript via headless Chromium, allowing client-side routers to hydrate and exposing dynamic routes, interactive forms, and internal API fetch requests.
- **Leaked Secret & Credential Scanning (`trufflehog`):**
  When `katana` or `gau` discover client-side JavaScript bundles (`.js`), API configs, or sensitive endpoints, pass those URLs to `trufflehog` to scan for high-entropy tokens, leaked private API keys, AWS/Azure credentials, and internal service URLs.
- **Technology-Aware Path Selection (`ffuf`):**
  Align wordlists and extension fuzzing with technologies identified in Known Facts:
  - For serverless / cloud functions / modern APIs (Node, Go, Python, Azure Functions, AWS Lambda): focus on API routes (`/api`, `/v1`, `/v2`, `/health`, `/status`, `/swagger`, `/openapi.json`, `/docs`) rather than legacy CMS/PHP admin pages.
  - For IIS / ASP.NET: test `.aspx`, `.asmx`, `.svc`, `/trace.axd`, `/elmah.axd`.
  - For WordPress / PHP: test `/wp-json/`, `/xmlrpc.php`, `/wp-admin/admin-ajax.php`.
- **API and REST Route Discovery (`kiterunner`):**
  When targeting modern web applications, microservices, or domains exposing API endpoints (e.g. `/api`, `/v1`, `/v2`, `/graphql`, `/rest`, or API gateways), run `kiterunner` with the target URL (`https://<target>`). `kiterunner` uses Kitebuilder routing schemas (`api-routes.kite`) to reconstruct hidden REST API routes, parameter expectations, and OpenAPI/Swagger documentation paths that flat wordlists miss.
- **Exposed Git Repository Extraction (`gitdumper`):**
  When path probing (`httpx_probe`, `ffuf`, `katana`, `nuclei`) detects an accessible `.git` directory or endpoint (e.g. HTTP 200, 301, or 403 on `/.git/` or `/.git/HEAD`), run `gitdumper` against the base URL (`https://<target>`). `gitdumper` dumps raw git index/pack files, runs checkout to reconstruct the repository source code on disk, and extracts recent commit messages, author emails, and exposed source files into evidence. Follow up on any discovered config files (`.env`, `database.php`, `config.json`) with `trufflehog` for credential extraction.
- **IDOR / Object Authorization Probing (`idor_probe`):**
  When `katana`, `gau`, `linkfinder`, or `arjun` surfaces endpoints with numeric or object identifiers (e.g. `?id=105`, `?order_id=402`, `?doc=99`, `?invoice_id=12`, or REST paths like `/api/v1/orders/105`), do not only test for SQLi/XSS. Run `idor_probe` with `target` to test for Insecure Direct Object References (BOLA/IDOR). `idor_probe` sends strictly read-only GET requests (capped at 3 candidate probes) and extracts the boilerplate-stripped differential (differing JSON keys or unique HTML lines). Inspect the extracted `diff_preview`: if the differing content exposes private customer records, internal invoices, or user PII across IDs without authentication or across accounts, log a finding with `log_finding`. If the diff shows only public catalog items, blog articles, or identical/soft-404 responses, no unauthorized object disclosure exists.
- **Precision HTTP Probing & PoC Verification (`http_request`):**
  When an automated scan suggests a vulnerability or when `searchsploit` yields a proof-of-concept requiring specific HTTP headers, methods, or payloads, use `http_request` to send precision requests directly. `http_request` allows setting exact `method`, `headers`, `data`, and `follow_redirects` without running heavy automated scanners. Use it to:
  1. Verify suspected access control or authorization bypasses (e.g. testing `/admin` or `/api` with custom `X-Forwarded-For`, auth tokens, or modified verbs).
  2. Test custom API request bodies (JSON, XML, form-data) on routes discovered by `kiterunner` or `katana`.
  3. Validate potential false positives reported by automated scanners before logging findings.
